# SA Service Delivery Agent - Test Plan

## 1. Objective

This document outlines the testing procedure for the new SA Service Delivery Agent (`sa_service_agent_v1`) and its integration within the Raizin Vault system, particularly its interaction with the MCP Node, Resonator Filter, and the user interface (`public/index.html`).

## 2. Testing Environment

*   **Supabase Project:** A deployed Supabase project with all Phase 6 functions:
    *   `sa_service_agent_v1` (new)
    *   `mcp_node` (updated with routing for SA Service Agent)
    *   `resonator_filter`
    *   `clarity_agent_v1`
    *   `innovation_agent_v1` (Gemini version)
    *   `log_user_feedback`
    *   Analytics functions (`get_agent_resonance_trends`, etc.)
*   **Database:** All database schema changes applied, including `agent_profiles_schema.sql` seeded with `sa_service_agent_v1`, `clarity_pulse_v1_001`, and `innovation_pulse_v1_001`. `interaction_log` table should have all columns from `interaction_log_enhancements.sql` and `phase5_schema_updates.sql`.
*   **Environment Variables:** All necessary environment variables must be correctly set for each Supabase function (e.g., `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `RESONATOR_FILTER_URL`, `GEMINI_API_KEY`).
*   **User Interface:** The `public/index.html` page should be accessible via a web browser, ideally served through Supabase or a local web server configured to proxy function calls if needed.
*   **Tools:** Browser developer console for observing JavaScript logs and network requests. Supabase dashboard for viewing `interaction_log` table entries and function logs.

## 3. Test Cases & Expected Outcomes

### Test Case 1: Service Discovery
*   **Action:** Open `public/index.html`. In the query input, type "what services do you offer?" and submit.
*   **Expected UI Response:**
    *   `agentIdDisplay`: Shows "Agent: sa_service_agent_v1".
    *   `responseDisplay`: Text from `sa_service_agent_v1` listing the two services: "I offer the following services: 1. Tender BOQ Assistance - ZAR 500.00 2. Website Design - ZAR 1500.00 Which service are you interested in?".
    *   `toneIndicator`: Reflects a generally positive/neutral tone (e.g., blue or green).
    *   Feedback buttons (👍/👎) become visible and enabled.
*   **Expected `interaction_log` Entry:**
    *   `routed_agent_id`: "sa_service_agent_v1"
    *   `input_text`: "what services do you offer?"
    *   `pre_filter_response`: Contains the raw list of services as generated by the agent.
    *   `agent_response_text`: Contains the (potentially filtered by Resonator) list of services.
    *   `filter_alignment_score`: Populated with a numeric value (e.g., between 0.0 and 1.0).
    *   `filter_value_alignment_details`: Populated with JSONB.
    *   `kb_article_slug`: "service_list" (or similar, based on agent's internal logic).

### Test Case 8: UI Feedback Test
*   **Action:** For any response where feedback buttons are visible (e.g., after Test Case 1), click the "👍" button. Then, for another interaction (e.g., after Test Case 2), click the "👎" button.
*   **Expected UI Response:**
    *   After clicking a feedback button, the `feedbackStatus` should display "Sending feedback..." then "Feedback sent! Thank you.".
    *   The feedback buttons should become disabled for that specific interaction to prevent re-submission.
*   **Expected `interaction_log` Update:**
    *   Locate the `interaction_log` row using the `interaction_id` that was displayed/available when the feedback was given.
    *   The `user_feedback_score` column for that row should be updated to `1` (for 👍) or `-1` (for 👎).
    *   The `updated_at` timestamp for that row should reflect the time of the feedback submission.

## 4. Verification Points for Each Test Case

For each test case, verify the following:

*   **Correct Agent Routing:**
    *   Does the `agentIdDisplay` in the UI show the expected agent ID?
    *   Does the `routed_agent_id` field in the corresponding `interaction_log` entry match the expected agent?
*   **Correct Response Content:**
    *   Is the text displayed in the UI (`responseDisplay`) appropriate for the query and the current stage of the service interaction (e.g., service listing, description, payment instructions, post-payment acknowledgement)?
*   **Payment Instructions (if applicable):**
    *   Is the Ozow link correct?
    *   Is the currency and price correct for the specified service?
    *   Is the payment reference format correct (e.g., `BOQ-[ID]`, `WEBDESIGN-[ID]`)?
*   **Resonator Filter Application:**
    *   Check the `filter_alignment_score` in the `interaction_log`. Does it seem reasonable for the type of response? (e.g., high for clear, scripted service info).
    *   Is the `agent_response_text` (post-filter text) sensible and well-formatted? Does it differ from `pre_filter_response` if the filter made changes?
    *   Are `filter_warnings` and `filter_value_alignment_details` populated?
*   **Logging Completeness:**
    *   Are all relevant fields in the `interaction_log` populated as expected (e.g., `input_text`, `input_desired_frequency_profile`, `pre_filter_response`, `pre_filter_confidence`, `kb_article_slug` (if applicable), `llm_metadata` (if applicable))?
*   **Error Checks:**
    *   Monitor the browser's developer console for any JavaScript errors.
    *   Monitor the Supabase function logs (for `mcp_node`, `sa_service_agent_v1`, `resonator_filter`, etc.) for any runtime errors or unexpected log messages.

## 5. Post-Test Activities
*   Document all test results, noting any deviations from expected outcomes.
*   Create bug reports or issues for any failures or discrepancies.
*   Review `interaction_log` entries to confirm data integrity and completeness.
